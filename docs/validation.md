# Отчёт фактической проверки

Проверено 10 ноября 2026 года по Europe/Minsk (события контейнеров — 9 ноября UTC). Windows 10, WSL2, Docker Desktop 4.33.1, Docker Engine 27.1.1, Compose 2.29.1. Docker выделено 8 307 650 560 байт RAM. Использовался только проект Compose `smart-logistics-de-test`.

## Что запускалось

1. Собраны Python-образ обязательного конвейера и образ Airflow 2.10.5. В обоих Dockerfile выполняется `pip check`; отдельная проверка установленного окружения Airflow также успешна: [dependency-check.txt](dependency-check.txt).
2. Первый прямой запуск обязательной части: генерация 300 000 сделок, ETL, витрина, CatBoost, скоринг — `PIPELINE_SUCCESS`, 40 тестов без ClickHouse.
3. Прямой запуск с ClickHouse — `PIPELINE_SUCCESS`, **41 passed**, 96,76 секунды pytest. Сравнены все строки и все показатели витрины PostgreSQL и ClickHouse.
4. Автоматический запуск через Airflow: 7 задач `success`, все с первой попытки, **41 passed**, errors=0, failures=0, skipped=0. JUnit: [pytest-first-airflow.xml](pytest-first-airflow.xml); состояния задач: [airflow-first-run.txt](airflow-first-run.txt).
5. Перезапущены scheduler/webserver и повторно выполнен `docker compose up -d --wait`. DAG Run остался один, со статусом success: [restart-verification.txt](restart-verification.txt).
6. После успешных проверок удалены все проектные контейнеры, сеть и четыре тома. Затем выполнен обычный `docker compose up -d` на пустых томах: metadata DB, источник, Core, Mart, модель и ClickHouse построены заново без ручного Trigger и дополнительных команд инициализации.
7. Чистый запуск DAG: **2026-11-09 22:07:13–22:10:57 UTC**, около 224 секунд вместе с генерацией, обучением и тестированием. Все 7 задач успешны с первой попытки. **41 тест за 99,357 секунды, 0 failures, 0 errors, 0 skipped**. Подтверждения: [airflow-clean-deployment.txt](airflow-clean-deployment.txt), [pytest-clean-deployment.xml](pytest-clean-deployment.xml).
8. Выполнен `sql/checks.sql` с `ON_ERROR_STOP=1`, включая блок исключений smoke-проверки: [sql-smoke.txt](sql-smoke.txt). Веб-страница входа Airflow вернула HTTP 200, scheduler и metadata DB — healthy: [airflow-health.json](airflow-health.json).

Первоначальная недоступность Docker Engine была устранена перезапуском Docker Desktop пользователем. При интеграции исправлены права старого тома модели, создание metadata DB вне транзакции, порядок начальной проверки соединения Airflow и конфликты зависимостей провайдеров. Чистый финальный запуск этих исправлений не потребовал ручных действий.

## Содержание 41 теста

Проверены границы и округление категорий, отрицательные/нулевые/нечисловые значения, валютная цена меньше 1000, точный курс и его отсутствие, неизвестный город, совпадающие города, исходные флаги, минимальный id города, M:N кузовов и fallback, уникальность зерна, отсечение будущих месяцев, независимые NumPy-перцентили/AVG/CV/перевозчики, календарные MoM/YoY и уровни надёжности, границы time split, исключение финансовых колонок из features, циклические признаки и будущие NULL.

Интеграционный тест выполнял полный повтор `source_init → etl → marts → training → scoring`, затем частичный backfill `2026-10-05`…`2026-10-10`. Хеши содержимого Core, карантина, связей, витрины и прогнозов совпали до и после; технический `scored_at` исключён. Отдельно проверен переход валидной записи в карантин после исправления цены. Тестовые строки удалены. ClickHouse сравнивался с PostgreSQL по каждой ячейке и каждому показателю, повторная загрузка дала тот же результат.

## Бонусы и ограничения

**Выполнены и проверены:** Airflow как реальный оркестратор с автозапуском, retries, параметрами периода и UI; ClickHouse MergeTree с атомарной синхронизацией и автоматической сверкой данных.

**Superset не реализован.** HTML во входных приложениях остаётся продуктовым прототипом. Синтетические данные не описывают реальный рынок; ночная разметка выбросов 26.10.2026 может запаздывать. Сложные будущие маршруты скорируются моделью, обученной на простых маршрутах. Прочие технические ограничения перечислены в [implementation-notes.md](implementation-notes.md).

## Итоговая очистка

После всех тестов удалены **5 контейнеров финального стенда, 1 сеть, 4 тома и 10 собственных образов**, включая промежуточные версии, созданные при исправлениях. Перед удалением контейнеров/томов/сети проверен Compose label; образы определены по специальному label и точным id из истории сборки. Перед удалением каждого образа проверено отсутствие использующих его контейнеров.

Инвентаризация: [cleanup-inventory.json](cleanup-inventory.json). Повторная проверка подтвердила **0 оставшихся проектных контейнеров, сетей, томов и собственных образов**: [cleanup-result.json](cleanup-result.json). Общие базовые образы и общий BuildKit cache не удалялись; глобальные prune не выполнялись.

Модель и базы данных были в удалённых томах; их исходники и генераторы остались в репозитории. Следующий `docker compose up` снова соберёт необходимые собственные образы и воспроизведёт конвейер. Сохранены лёгкие отчёты проверки, а не большие датасеты или веса модели.

Все 7 оригинальных файлов остались неизменными, копии совпадают побайтно: [source-integrity.json](source-integrity.json), [source-hashes.json](source-hashes.json). Локальный Git-репозиторий инициализирован на ветке main; удалённая публикация не выполнялась.
